# mycelium

## Verdict
This is worth a product owner's time if the team is already using AI agents to move from idea to implementation. Mycelium's value is not that it writes more artifacts, but that it forces discovery, evidence, and decision gates before an agent is allowed to build. If your team is not using Claude Code or agentic delivery workflows, this is probably too much machinery.

## What It Is
Mycelium is a theory-guided product development harness for AI agents. In practice, it is a Claude Code plugin and framework containing namespaced skills, hooks, docs, schemas, templates, orchestration files, and a product canvas under `.claude/`. It is not a normal roadmap app or ticket tracker. It is a structured way to make an agent gather evidence, map opportunities, record decisions, and pass gates before moving into implementation.

## Why It Is Useful For Product Owners
For backlog refinement, it helps prevent vague requests from becoming implementation tasks before the problem, user, and evidence are clear. For discovery, it includes mechanisms around interviews, Jobs to be Done, opportunity mapping, and theory-backed decision gates. For stakeholder alignment, the canvas and decision log create a written trail of why the team is building something. For roadmap planning and prioritization, it gives a PO a way to challenge weak ideas before they consume delivery capacity. For delivery coordination, it connects product reasoning to implementation context so agents and engineers are not working from disconnected prompts.

## How I Would Actually Use It
1. Run `/mycelium:start` on a messy product idea and use the opening discovery interview to expose missing user, evidence, and business context.
2. Use the canvas files as the source of truth for assumptions, decisions, and current product state before creating stories or tasks.
3. Use the JTBD and opportunity mapping flow before roadmap planning so the team prioritizes user progress, not stakeholder volume.
4. Use the evidence gates as a hard stop when a feature request lacks proof that the problem is real.
5. Use the decision log during stakeholder reviews to show what was accepted, rejected, and why.
6. Use the evaluation guide before rollout to decide whether the structure is worth the adoption cost for the team.
7. Use the theory mapping docs as a sanity check when the team is applying frameworks loosely and pretending that counts as product discipline.

## Limitations / Watch Outs
The setup is not lightweight. It brings its own vocabulary, schemas, gates, and operating model, so a casual PO will bounce off it fast. The strongest path is Claude Code plugin usage; other agent runtimes get less of the enforcement layer. Star count is modest, so community proof is still thin. It can also become process theater if the PO treats gates as boxes to fill instead of using them to kill weak work.
