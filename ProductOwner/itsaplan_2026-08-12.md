# itsaplan

## Verdict
This is genuinely worth a product owner's time if the team wants an owned alternative to Linear, Jira, Plane, or Trello with AI-agent work built into the same operating surface. It is not a casual template repo: it is a real self-hosted tracker with issues, views, dashboards, initiatives, API, webhooks, MCP, and agent assignment. The catch is blunt: it is young, pre-1.0, and needs engineering ownership to run safely.

## What It Is
itsaplan is a self-hosted project management and issue-tracking application. It is a software product, not a curated list or template library. The repo includes a Next.js web app, Elysia API, worker service, Telegram bot, PostgreSQL schema and migrations, MinIO-backed storage, auth packages, Docker compose files, self-hosting docs, development docs, a changelog, and CI configuration.

## Why It Is Useful For Product Owners
For backlog refinement, it supports configurable issue types, custom fields, labels, states, subtasks, checklists, links between issues, and project-specific workflow settings. For prioritization and roadmap planning, it provides Kanban, table, timeline, calendar, initiatives, dashboards, and reusable saved views. For stakeholder alignment, it supports public read-only links to issues or views, notifications, dashboards, and shared project surfaces. For delivery coordination, it supports cycles, assigned issues, role-based access, activity history, GitHub pull request closure, webhooks, API keys, and MCP access. For experimentation with AI-assisted product work, agents can be members of the project with configured tools, skills, prompts, schedules, and permissions.

## How I Would Actually Use It

1. Set up a small pilot project for one product area, not the whole company, and model the actual workflow states: Backlog, Ready, In Progress, Review, Done, and Canceled.
2. Add issue types for feature, bug, discovery task, tech debt, experiment, and stakeholder request so intake is sortable without adding process theater.
3. Build saved views for refinement, launch readiness, blocked items, stakeholder-facing roadmap, and this sprint's delivery risk.
4. Use initiatives to group work by outcome or bet, then review whether issues are still connected to the initiative goal before sprint planning.
5. Share public read-only views with stakeholders instead of sending status screenshots or manually written roadmap updates.
6. Configure one AI agent for backlog hygiene, such as finding thin descriptions, missing acceptance criteria, stale blockers, or unlinked subtasks.
7. Use webhooks or the REST API to connect delivery status to release notes, support escalations, or customer-facing feedback loops.

## Limitations / Watch Outs
This is pre-1.0 software and the README explicitly warns to expect breaking changes before a stable release. Self-hosting is not free operationally: it needs Docker, a domain behind a TLS-terminating reverse proxy, secrets, PostgreSQL, MinIO, API, worker, bot, web services, backups, updates, and someone accountable for uptime. AGPL-3.0 matters if the company modifies and runs it as a network service. It also has modest community proof today, so do not bet a critical enterprise workflow on it without a pilot and rollback plan.
