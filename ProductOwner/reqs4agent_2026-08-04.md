# reqs4agent

## Verdict
This is worth a product owner's time if the team struggles with fuzzy requirements, scattered discovery notes, or agent-written backlog junk. It is not popular yet, but the repo has the right kind of practical value: source-backed Markdown requirements, human approval gates, open questions, templates, and validation. Treat it as a lightweight requirements operating system, not as a full Jira or roadmapping replacement.

## Why This Repo Was Picked
This repo won because it gives a PO a concrete way to turn business input into a governed requirements tree: vision, roadmap, domains, epics, features, and user stories. The templates force source references, owner fields, status, parent links, open questions, and acceptance criteria instead of letting an AI invent detail. The playbooks also include explicit human stop points before generating or approving artifacts, which is exactly where product ownership belongs.

## What It Is
`reqs4agent` is a template repository for building a Markdown and YAML requirements repo. It contains playbooks for bootstrap, ingest, and maintenance; templates for vision, roadmap, epic, feature, and user story artifacts; a requirements contract; validator scripts; and a worked end-to-end bakery fleet example. It is a framework and template kit, not a hosted app.

## Why It Is Useful For Product Owners
For backlog refinement, it creates a traceable path from raw business input to epics, features, and user stories. For acceptance criteria, it pushes teams to keep binding sections sourced and testable, with missing detail recorded as open questions. For discovery and stakeholder alignment, it makes product gaps visible before delivery starts. For roadmap planning, it links roadmap items back to visions and goals. For delivery coordination, it gives engineers and agents a consistent contract without letting implementation notes become fake requirements.

## How I Would Actually Use It
1. Start a new product requirements repo before a discovery-to-delivery handoff, then run the bootstrap playbook to define domains, domain codes, glossary, and the first vision.
2. Drop a BRD, interview notes, sales notes, or discovery transcript into `inbox/`, then use the ingest playbook to propose a domain, epic, feature, and story tree.
3. Review the generated proposal before any artifacts are written, especially unmapped items and open questions.
4. Use the user story template to force `As a`, `I want`, `So that`, acceptance criteria, source, owner, status, and parent feature fields.
5. Use open questions as a PO follow-up list before calling anything sprint-ready.
6. Run `scripts/validate.py` before handoff so broken parent links, missing mirrors, weak IDs, and release mismatches are caught mechanically.
7. Use the worked bakery fleet example to calibrate expectations: the first pass should create a validated skeleton, not pretend to finish the product spec.

## Limitations / Watch Outs
The repo is very young, with no stars or forks at scan time, so there is little community proof. It is not a backlog board, discovery repository, analytics tool, or stakeholder-facing roadmap product. Teams need comfort with Git, Markdown, YAML frontmatter, Python dependencies, and agent-assisted workflows. The value is high only if the team will actually maintain the contract; if people keep making decisions in Slack and never update the repo, this becomes process theater.
