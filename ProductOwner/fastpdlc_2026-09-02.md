# fastpdlc

## Verdict

FastPDLC is worth a product owner's time when product decisions, rules, and requirements need to stay aligned with implementation. It gives a team a practical contract for typed Markdown artifacts, cross-reference validation, generated product bundles, CI drift checks, and audit evidence. It is not a backlog or roadmap tool, and the agent orchestration is optional and developer-heavy, so use it as a product-definition quality gate rather than a replacement for Jira, Linear, or a discovery system.

## What It Is

FastPDLC is a Python CLI and library for product-as-code. A team defines artifact types in `product.config.yaml`, writes Markdown files with frontmatter under a product directory, and runs `fastpdlc build` and `fastpdlc validate`. The validator checks required fields, ID conventions, enums, references, and stale generated bundles, then emits stable `PAC-NNN` diagnostic codes.

It also includes an optional agent-built lifecycle for one artifact: understand, human disambiguation, design, develop, test, and adversarial verification. The lifecycle can propose or optionally write changes through a bounded file tool loop. The repository further includes an evidence command that records hashes, commit context, and validation results, plus plugin hooks for project-specific checks and generated outputs.

## Why It Is Useful For Product Owners

- Backlog refinement: turn feature, rule, decision, glossary, and constraint records into typed artifacts with required fields.
- User stories and acceptance criteria: add artifact types and references that require the story to point to valid rules, terms, or related features.
- Stakeholder alignment: make business terminology and durable decisions visible in version control instead of leaving them in meeting notes.
- Roadmap planning: represent feature status, dependencies, and target fields as validated data that can feed a generated bundle or custom report.
- Delivery coordination: use `PAC-060` staleness failures to catch when committed product documentation no longer matches the source artifacts.
- Metrics and auditability: use content-addressed evidence records when a regulated or high-risk team must show what was checked and against which commit.
- Discovery handoff: stop an agent or team at a human disambiguation gate when open questions would make a technically correct implementation solve the wrong problem.

## How I Would Actually Use It

1. Start with a small `product/` directory containing terms, business rules, decisions, and features for one regulated workflow. Define only the fields the team will maintain.
2. Add `fastpdlc validate` to pull requests so missing fields, broken references, invalid enums, and stale generated bundles fail before delivery review.
3. Link feature artifacts to business rules and glossary terms, then review the generated JSON bundle with engineering and design as the shared product contract.
4. Add a plugin validator for PO-specific evidence, such as requiring every feature to name an outcome metric, owner, decision record, or linked implementation path.
5. Run `fastpdlc evidence -o build/evidence.json` for a release candidate, then verify that record during a later audit or incident review.
6. Use the optional orchestrator in dry-run mode to expose unanswered questions and adversarial findings before a developer starts work. Keep `--write` off until the team trusts the workflow.
7. Scaffold a pilot with the [Copier template](https://github.com/tarvitave/fastpdlc/blob/main/copier.yml), then compare the maintenance cost against the defects and clarification churn it prevents.

## Limitations / Watch Outs

- The repository is very young, with 0 stars, 1 fork, 0 open issues, and a current version below 1.0. Community proof is weak.
- It is not a backlog, roadmap, feedback, analytics, or stakeholder collaboration product. A PO still needs those systems elsewhere.
- Adoption requires Git, Python, YAML, Markdown frontmatter, and a team willing to treat product artifacts as maintained code.
- The optional agent lifecycle needs the `agents` extra and an `ANTHROPIC_API_KEY`; model calls add cost, provider dependency, and review obligations.
- The agent writer is intentionally constrained and cannot run tests, merge changes, use a shell, or access the network. A green product validation result is not a substitute for application CI.
- The LGPL license is more flexible than a strong copyleft application license, but legal review is still appropriate before embedding or redistributing it in a commercial product.
- The generated bundle and schema can become another layer of ceremony if the team models every idea instead of focusing on durable decisions, rules, and delivery-critical requirements.
