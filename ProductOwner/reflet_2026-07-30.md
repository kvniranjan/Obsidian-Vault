# reflet

## Verdict
Reflet is worth a product owner's time if user feedback is scattered across support, Slack, sales calls, and random docs. It gives you a practical loop for collecting requests, letting users vote, shaping a roadmap, and publishing changelog updates. Do not oversell it: the repo is young, the community signal is thin, and self-hosting is an engineering job.

## What It Is
Reflet is an open-source product feedback and roadmap application. The repo contains a Next.js web app, Convex backend, feedback and changelog widget packages, SDK package, MCP server package, shared UI/config packages, contributor docs, and AI-agent instruction folders. It is software you can run or evaluate as a feedback portal, not just a template library.

## Why It Is Useful For Product Owners
Reflet fits PO work where customer signals need to become decisions. Feedback boards support intake and discovery. Voting and comments help separate isolated opinions from repeated demand. Tags, search, and roadmap status help backlog refinement and prioritization. Changelog and release links support stakeholder alignment after delivery. Private boards can hold internal triage while public boards keep customers informed.

## How I Would Actually Use It
1. Create one public feedback board per product area and route support, sales, and customer success requests into it instead of keeping them in scattered docs.
2. Use votes, comments, and tags as input to backlog refinement, then link the top feedback items to epics or Jira tickets.
3. Maintain a roadmap board with statuses like Backlog, Planned, In Progress, and Done so stakeholders can see what is moving without another status deck.
4. Run a monthly feedback review: filter by vote count, recent comments, customer segment, and roadmap status, then pick the items that deserve discovery work.
5. Publish changelog entries that close the loop with users who requested a shipped feature.
6. Use private boards for internal product bets, competitive responses, or enterprise-customer requests that should not be public.
7. Ask engineering to evaluate the widget, SDK, and MCP packages if the goal is to capture feedback inside the product and connect it to internal workflows.

## Limitations / Watch Outs
- The repo is young and has modest community proof: 32 stars and 1 fork at scan time.
- SSPL is not a casual license. Legal and engineering should review it before commercial self-hosting or modification.
- Self-hosting needs Bun, Node.js, Convex setup, environment variables, and engineering ownership.
- It is not a full product management suite. It will not replace Jira, Linear, Aha, Productboard, analytics, or research repositories by itself.
- GitHub has no release object, so maturity and upgrade cadence must be judged from commits and docs.
- Public voting can distort prioritization if loud users are not representative of revenue, strategy, risk, or target-market fit.
