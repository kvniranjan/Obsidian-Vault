# feedlog

## Verdict
FeedLog is worth a product owner's time if the team needs a real feedback-to-roadmap-to-changelog loop and can use the hosted product or fund deployment. It is an actual operating tool, not a reading resource: customers can submit and discuss feedback, while the team can triage, roadmap, support, and communicate shipped work. The blunt catch is that self-hosting is still an engineering project, and the public signal can distort priorities if the PO treats votes as evidence of value.

## What It Is
FeedLog is an open-source customer-support and product-feedback application. It is software, not a template library or prompt pack. The repo contains a Nuxt and TypeScript application, AI support agent, help center, shared inbox, feedback boards, roadmap, changelog workflow, Docker setup, deployment guides, configuration docs, tests, and a hosted demo.

## Why It Is Useful For Product Owners
FeedLog gives a PO a shared operating surface for customer feedback instead of scattering requests across Slack, email, sales notes, and support tickets. The feedback boards support discovery and backlog refinement by turning raw requests into visible, discussable candidate work. Voting, comments, similar-idea detection, and support context help with prioritization and stakeholder alignment, while roadmap states and changelog entries make delivery communication concrete. The help center and inbox also let a PO see recurring product confusion and support pain before turning it into a feature request.

## How I Would Actually Use It
1. Create separate feedback boards for bugs, feature requests, and improvements, then define the triage labels and owner for each board.
2. Review the shared inbox weekly and convert recurring support questions into help-center gaps, product bugs, or discovery candidates.
3. Merge similar ideas before refinement so duplicate requests do not inflate apparent demand.
4. Use votes and comments as one prioritization input, then add customer segment, revenue impact, strategic fit, and effort in the PO decision record.
5. Move selected items through roadmap states before sprint planning so stakeholders can distinguish feedback, discovery, planned work, and committed delivery.
6. Link a changelog entry to the feedback that motivated the release, then notify or follow up with the users who asked for it.
7. Run the hosted demo with support and engineering for one week before deciding whether self-hosting is worth the operational cost.

## Limitations / Watch Outs
The hosted path is the practical starting point, but self-hosting expects PostgreSQL 17+ with `pgvector`, auth secrets, admin email setup, and optional email, OAuth, S3, and OpenAI-compatible configuration. It is still pre-1.0, so minor releases can carry breaking changes and the AI support layer needs careful grounding and escalation rules. FeedLog is also not a full product backlog, delivery tracker, experiment platform, or analytics system. Public votes can amplify loud users, and support volume is not the same as product value, so the PO still needs segmentation, strategy, qualitative research, and a system of record for committed work.
