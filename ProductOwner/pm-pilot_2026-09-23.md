# pm-pilot

## Verdict

Yes, this is worth a product owner's time if the team already uses Claude Code or is willing to adopt it. It packages real PM workflows for discovery, PRDs, prioritization, meeting preparation, status reporting, stakeholder context, market sizing, and bug triage, instead of stopping at generic prompts. The catch is that its strongest workflows depend on Claude Code and optional MCP connections, so it is not a drop-in replacement for Jira, Linear, a research repository, or a product analytics stack.

## Why This Repo Was Picked

The winner is operationally useful across a PO's week: `pm-core` covers PRDs, prioritization, market sizing, meeting prep, stakeholder intelligence, weekly status, and critique; `pm-discovery` produces interview snapshots, evidence-backed synthesis, opportunity trees, and stakeholder one-pagers; and `bug-shepherd` can triage stale Jira, Linear, or GitHub issues with human approval gates. It also has a one-line marketplace install, plain Markdown skills that can be read or adapted, recent releases, and a concrete safety model for tracker writes. That combination beat smaller template libraries and repositories that only explain product methods.

## What It Is

pm-pilot is a collection of Claude Code plugins made mostly from Markdown skills, rules, agents, templates, examples, and configuration. It is not a standalone PM application or a hosted backlog system. The repository provides installable workflows for product thinking and delivery support, with optional MCP connections to Jira, Slack, Calendar, GitHub, Confluence, and Granola for context retrieval.

## Why It Is Useful For Product Owners

- Backlog refinement: use `critique`, `prd`, and `prioritize` to expose missing context, rank options, and turn messy thinking into structured work.
- User stories and acceptance criteria: use the PRD and critique workflows to clarify scope, non-goals, risks, and evidence before handing work to engineering.
- Discovery: use interview snapshots, Mom Test interview guides, quote verification, synthesis, and opportunity trees to connect research to decisions.
- Prioritization: compare RICE, ICE, WSJF, MoSCoW, Kano, or Value/Effort using a consistent decision frame rather than stakeholder volume.
- Stakeholder alignment: use meeting prep, people sync, stakeholder memory, and one-pagers to carry commitments and objections forward.
- Roadmap and metrics: use outcome-oriented planning, market sizing, weekly status, and decision briefs to make assumptions and progress visible.
- Delivery coordination: use bug-shepherd's reproduce, review, and approval gates to reduce stale-ticket noise without silently changing the tracker.

## How I Would Actually Use It

1. Install `pm-core`, connect read-only Jira and Slack access, and run `pm-core:brief` on a disputed feature before the next prioritization meeting.
2. Run `pm-discovery:interview-snapshot` for each customer transcript, then synthesize only the structured snapshots so unsupported quotes are flagged instead of polished into fake evidence.
3. Use `pm-core:prd` after a raw team braindump to produce a one-pager with the problem, non-goals, success measures, risks, and open questions.
4. Run `pm-core:prioritize` on a short feature list with the method that matches the decision, then record the assumptions behind reach, impact, confidence, and effort.
5. Run meeting prep before a stakeholder review and compare the generated commitments with the previous meeting's people files before making a promise.
6. Generate `weekly-status` from completed tickets and merged work, then manually check the omissions before sending it to leadership.
7. Use bug-shepherd in review-only mode against a stale issue slice, inspect every proposed cancellation, and approve only the explicitly listed batch.

## Limitations / Watch Outs

- It is Claude Code-first. Plain Markdown makes adaptation possible, but the polished install and namespaced commands assume Claude Code or Cowork.
- The useful integrations require MCP setup and permissions. Without Jira, Slack, Calendar, GitHub, or Granola connections, several workflows fall back to user-supplied files and context.
- This is an assistant layer, not a source of truth. A PO still owns evidence quality, prioritization judgment, access boundaries, and final tracker changes.
- The repository is young and small by community standards: 17 stars, 4 forks, 1 open issue, and limited independent usage evidence.
- Market sizing and research synthesis can still be wrong even when the workflow demands sources or verifies direct quotes. Verification is a guardrail, not proof that the underlying evidence is representative.
- Some features expose sensitive stakeholder or organizational context. Keep memory files local and review MCP scopes before connecting company systems.
- The exact repository creation timestamp was not available in the accessible GitHub page, and the latest activity date came from indexed GitHub metadata rather than a direct API response.
