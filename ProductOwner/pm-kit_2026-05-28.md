# pm-kit

## Verdict
This is worth a product owner's time if they already live in Obsidian and are willing to use an AI coding agent as a working PM assistant. It is not a casual reading repo. The value is in its reusable operating system for dailies, blockers, decisions, PRDs, meeting extraction, weekly reviews, and project memory.

## Why This Repo Was Picked
`pm-kit` won because it is built for actual day-to-day product work, not just product education. It gives a PO a markdown-based system for daily status, blockers, decisions, documents, meetings, inbox capture, weekly reviews, project health, and cross-project progress. The Obsidian fit is unusually strong for this vault, and the repo explicitly supports multiple agent environments, including OpenAI Codex through `AGENTS.md`.

It also beat more polished or more popular alternatives because it is operational. A PO can use it tomorrow to capture a blocker, turn meeting notes into actions, draft a spec, or answer "what did we decide about auth?" from project memory.

## What It Is
`pm-kit` is a markdown-first PM workspace and template system for Obsidian plus AI coding agents. It contains folders for inbox capture, indexes, templates, blockers, daily notes, decisions, docs, meetings, reports, scripts, and agent configuration files.

The repo provides command workflows such as `/today`, `/daily`, `/progress`, `/block`, `/decide`, `/doc`, `/meet`, `/inbox`, `/ask`, `/health`, `/weekly`, `/push`, `/onboard`, and `/update`. It is a working system, not just a checklist.

## Why It Is Useful For Product Owners
- Backlog refinement: use `/doc` to draft PRDs or specs, then connect them to decisions and blockers.
- Delivery coordination: use `/daily`, `/today`, and `/progress` to keep shipped work, WIP, and blockers visible.
- Stakeholder alignment: use `/decide` to record tradeoffs, alternatives, and final calls before they get lost in Slack.
- Discovery and requirements: use `/meet` to extract decisions, blockers, and action items from raw meeting notes.
- Roadmap planning: use `/weekly` to roll daily evidence into sprint-level reflection and next priorities.
- Metrics and follow-through: use `/health` and `/ask` to find broken project memory, missing links, and prior rationale.
- Cross-functional clarity: store decisions, blockers, dailies, docs, and meeting outputs in one browsable Obsidian vault.

## How I Would Actually Use It
1. Run `/onboard` for one active product area and let it create the initial project context.
2. Start each morning with `/today` or a quick `/daily checkout: shipped X, wip Y, blocked on Z` entry.
3. After refinement, run `/doc checkout-flow` to create a spec, then manually tighten acceptance criteria before sharing it.
4. During stakeholder conflict, use `/decide checkout: chose account-level pricing over seat pricing` and capture rejected options.
5. Paste meeting notes into `/meet checkout sync sprint-review` and let it split actions, decisions, and blockers.
6. Run `/weekly` every Friday to generate a sprint retro and identify the next priority instead of relying on memory.
7. Use `/ask what did we decide about auth?` before reopening old debates.

## Limitations / Watch Outs
- The default flow assumes Claude Code. It claims compatibility with Codex, Cursor, GitHub Copilot, Windsurf, and Cline, but the smoothest path is still Claude-first.
- Setup is not trivial for a non-technical PO. Git, Obsidian, terminal usage, and optionally QMD/Bun are real friction.
- The repo has modest adoption, so do not treat it as a mature industry standard.
- A PO still needs judgment. The system can structure work, but it will not make weak strategy or vague requirements good by itself.
- The optional semantic `/ask` path requires QMD and extra CLI setup. Without that, search falls back to simpler vault lookup.
