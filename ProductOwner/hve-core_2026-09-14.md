# hve-core

## Verdict

Yes, this is worth a product owner's time if the team already uses GitHub Copilot and keeps product artifacts in a repository. Its project-planning collection connects discovery, PRDs, BRDs, acceptance criteria, traceability, experiments, backlog planning, and delivery handoff. It is not a roadmap or backlog product, and adopting the whole repo would be excessive.

## What It Is

hve-core is a GitHub Copilot customization framework, not a hosted product-management application. It bundles agents, prompts, instructions, skills, documentation, scripts, and an extension for an opinionated agentic software development lifecycle.

For a PO, the useful slice is `.github/skills/project-planning`. It contains reusable workflows for backlog management and planning, PRD and BRD authoring, product discovery, outcome hypotheses, experiments, privacy, security, architecture review, and work-item planning. The materials are repository-native Markdown and agent instructions, so they can be inspected, adapted, and versioned.

## Why It Is Useful For Product Owners

- Backlog refinement: turn approved requirements into smaller work-item candidates and preserve the reasoning behind the split.
- User stories and acceptance criteria: use structured requirement identifiers and testable acceptance guidance instead of vague completion language.
- Discovery: capture personas, journeys, evidence sources, assumptions, and open questions before committing to a solution.
- Prioritization: force goals, outcomes, constraints, and measurable success signals into planning before sequencing work.
- Stakeholder alignment: use BRD discovery and approval gates to expose scope boundaries, decision owners, dependencies, and unresolved questions.
- Roadmap planning: connect outcome hypotheses, PRDs, backlog plans, and downstream GitHub, Jira, or GitLab work-item paths.
- Metrics and experimentation: use outcome hypotheses and experiment-design workflows to define the signal, baseline, target, and decision rule before launch.
- Delivery coordination: keep requirements, review findings, architecture decisions, and handoff artifacts linked in version control.

## How I Would Actually Use It

1. Install or copy only the `project-planning` assets into one product repository; do not adopt the entire engineering framework by default.
2. Use the Product Manager Advisor to pressure-test a request for the user problem, evidence, outcome, non-goals, constraints, and smallest testable slice.
3. Use the PRD discovery references to draft a persona and journey map, then trace each important pain point to evidence, a requirement, or an open question.
4. Run the requirements author workflow to produce a PRD with explicit goals, functional requirements, non-functional requirements, acceptance criteria, and source provenance.
5. Write an outcome hypothesis and experiment plan before ranking a risky initiative, including baseline, target, timeframe, owner, and what would change the decision.
6. Use backlog planning after approval to convert the PRD into scoped work items, dependencies, and a handoff package for the team's GitHub, Jira, or GitLab process.
7. Keep the PRD, review findings, decisions, and handoff payload in version control so roadmap changes have an inspectable decision record.

## Limitations / Watch Outs

- It is tightly coupled to GitHub Copilot conventions, repository files, and Microsoft tooling. Codex, Claude, Linear, and non-Git workflows require adaptation.
- It is not a backlog UI, roadmap visualization, customer-feedback system, analytics product, or stakeholder collaboration space.
- The repository is large and engineering-oriented. A PO should adopt a narrow collection and ignore unrelated security, implementation, and extension assets.
- The PRD flow can create process overhead for small changes. Use it for meaningful initiatives, not every bug fix or copy edit.
- The repo has 221 open issues. That shows active use, but it also signals an unfinished and changing surface.
- Repository-level MIT licensing does not mean every file has the same terms. Check frontmatter and third-party notices before copying content into a commercial system.
- AI-generated requirements remain hypotheses until a PO validates them with users, data, and stakeholders. The framework cannot manufacture missing evidence.
- Microsoft describes HVE Core as rapidly evolving and potentially incompatible across changes. Treat it as a pattern library you own, not a production dependency you blindly install.
