# hve-core

## Verdict

Yes, this is worth a product owner's time if the team already uses GitHub Copilot and is willing to keep product work in the repository. Its project-planning collection is more than a prompt list: it has guided BRD and PRD agents, lifecycle gates, discovery references, traceability identifiers, review artifacts, and work-item handoff. It is not a backlog system, and a PO who wants a visual roadmap or stakeholder workspace will need another tool.

## What It Is

hve-core is a GitHub Copilot customization framework. It bundles agents, prompts, instructions, skills, plugins, documentation, scripts, and an extension for AI-assisted engineering and product workflows.

For a PO, the relevant part is the `project-planning` collection. It includes a Product Manager Advisor, PRD Builder, BRD Builder, PRD Quality Reviewer, discovery references, EARS acceptance guidance, traceability naming, PRD and BRD templates, architecture planning, and work-item planning. It is a repository-native operating layer, not a hosted product-management application.

## Why It Is Useful For Product Owners

- Backlog refinement: turn an approved PRD into clearer, smaller work-item candidates and keep refinement planning separate from implementation.
- User stories and acceptance criteria: use stable FR, NFR, goal, and acceptance-criteria identifiers instead of vague prose.
- Discovery: capture users, journeys, evidence provenance, assumptions, and open questions before committing to a solution.
- Prioritization: force product goals and measurable success criteria into the PRD before work-item sequencing.
- Stakeholder alignment: use BRD discovery and approval gates to make business context, scope, and unresolved decisions explicit.
- Roadmap planning: carry an approved BRD into a PRD and then into downstream ADO, GitHub, or Jira planning artifacts.
- Delivery coordination: use quality review findings, traceability, architecture decisions, and handoff contracts to reduce loss of context between product and engineering.

## How I Would Actually Use It

1. Install only the `project-planning` collection in a product repository rather than adopting the entire framework.
2. Ask `product-manager-advisor` to pressure-test a feature request: user, pain, evidence, success metric, non-goals, and the smallest testable slice.
3. Run `prd-builder` to turn the surviving request into a seven-phase PRD, pausing when the evidence or scope is not good enough.
4. Require every functional requirement to carry a goal link, an acceptance criterion, and a source label such as user research, analytics, stakeholder input, or assumption.
5. Use the discovery reference to create a persona and journey map, then challenge each pain point against evidence before adding requirements.
6. Run the PRD Quality Reviewer before refinement and export the approved requirements into the team's native GitHub, Jira, or Azure DevOps work-item flow.
7. Keep the PRD, review findings, decisions, and handoff payload in version control so later roadmap or scope changes have an inspectable record.

## Limitations / Watch Outs

- It is tightly coupled to GitHub Copilot conventions, repository files, and Microsoft tooling. Codex, Claude, Linear, and non-Git workflows will need adaptation.
- It is not a backlog UI, roadmap visualization, customer-feedback system, analytics product, or stakeholder collaboration space.
- The repository is large and engineering-oriented. A PO should install a narrow collection and ignore unrelated security, implementation, and extension assets.
- The PRD flow can create process overhead for small changes. Use it for meaningful initiatives, not every bug fix or one-line copy change.
- The repo has 200 open issues. That is evidence of active use, but it also means the surface area is still moving and some guidance may change.
- Repository-level licensing is MIT, but the product-planning content declares CC BY 4.0 in places. Review the exact file license and preserve attribution before copying content into a commercial internal system.
- AI-generated requirements remain hypotheses until a PO validates them with users, data, and stakeholders. The framework cannot supply missing evidence.
