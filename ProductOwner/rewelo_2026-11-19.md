# rewelo

## Verdict

rewelo is worth a product owner's time if backlog prioritization is currently a spreadsheet argument with no durable scoring history. It gives a PO a working relative-weight backlog, dependency-aware capacity planning, ranking-change reports, and flow metrics through a local CLI or MCP server. It is still experimental, has only 2 stars and 0 forks, and should be piloted on a copy of a backlog rather than treated as a production system of record.

## What It Is

rewelo is a TypeScript command-line application backed by embedded SQLite. It is not a template library or a generic curated list. A project contains tickets with four Fibonacci-scale inputs, flexible `prefix:value` tags, relations such as `blocks` and `depends-on`, revision history, configurable weights, and event data. The same application can run as an MCP server for AI clients, or generate a self-contained HTML dashboard.

## Why It Is Useful For Product Owners

- Backlog refinement: capture each item with a consistent benefit, penalty, estimate, and risk vocabulary instead of an unstructured priority label.
- Prioritization: compare the whole backlog with relative weights, custom factor weights, value-to-cost priority, filters, and what-if simulation.
- Roadmap planning: group work with feature tags and use `plan_capacity` to fit ranked work plus required blockers into a capacity limit.
- Delivery coordination: record dependencies and expose priority inversions where a lower-ranked dependency blocks higher-ranked work.
- Stakeholder alignment: export CSV or JSON and use the formula, score history, and ranking-change report to explain why an item moved.
- Metrics: inspect lead time, cycle time, flow percentiles, forecast ranges, stale scoring, and whether estimates correlate with cycle time.
- Experimentation and learning: use `simulate` to test score or scope changes before changing the real backlog.

## How I Would Actually Use It

1. Export a current backlog to CSV, map title, description, benefit, penalty, estimate, risk, and tags, then import it into a throwaway rewelo project.
2. Run `rw ticket list --project Product --sort priority` during refinement and challenge the top and bottom items against the same four scoring dimensions.
3. Add `feature:`, `team:`, and `state:` tags, then compare average priority by feature before roadmap or quarterly planning.
4. Record `depends-on` and `blocks` relations, run `rw calc plan --capacity 20`, and review which blockers are pulled into the proposed sprint.
5. Use `simulate` or one-off weight overrides to show how rankings change when risk, customer penalty, or strategic benefit matters more.
6. Generate `rw report changes --since 2026-11-12` before a stakeholder review so the discussion focuses on changed assumptions rather than unexplained rank movement.
7. After several sprints, review `report flow`, `report times`, `report forecast`, and `report estimates` to see whether the team's scoring and estimation habits are useful.

## Limitations / Watch Outs

- The README explicitly calls the software experimental, unsupported, and not intended for production use.
- Adoption evidence is weak: 2 stars, 0 forks, and 2 open issues do not prove that the model works for real teams.
- The relative-weight formula is a decision aid, not objective truth. Bad inputs, political scoring, or false precision can produce a neat but wrong ranking.
- It is not a stakeholder-facing tracker and does not replace Jira, Linear, Azure DevOps, analytics, customer-feedback systems, or a roadmap communication surface.
- The npm path requires Node.js 24 or newer. The MCP path adds Docker or local MCP configuration and a persistent database-volume decision.
- Tags are flexible but require discipline. Teams still need their own definitions for states, score calibration, ownership, and review cadence.
- The tool is heavily oriented toward CLI, Git, and AI-assisted workflows. A PO who needs a polished collaborative UI will find the setup and interaction model too technical.
