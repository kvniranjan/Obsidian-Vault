# umami

## Verdict
Umami is worth a product owner's time if the team needs lightweight product and web analytics without buying into a heavy analytics suite. It will not run your roadmap or replace a deep experimentation platform, but it gives a PO enough signal to challenge gut-feel prioritization with usage, journeys, cohorts, funnels, retention, heatmaps, and revenue reports.

## Why This Repo Was Picked
Umami won because it gives a PO a practical way to answer basic product questions without waiting for a full data platform: where users enter, which pages or flows they use, where journeys drop, which segments behave differently, and whether changes move meaningful usage. The recent v3.2.0 release added heatmaps, stronger session replay controls, richer event and session property reporting, and revenue report improvements, which makes it more useful for product decisions than a plain traffic dashboard. It is also MIT licensed and actively maintained, so the setup burden is easier to justify than archived product-management tools or narrow PRD templates.

## What It Is
Umami is an open-source analytics platform. It is mainly a software product, not a template library or reading list. The repo contains the application code, Docker assets, database migrations, tracker code, tests, and deployment files for running a privacy-focused analytics stack.

The product covers web analytics, product events, audience segmentation, user journeys, funnels, retention, cohort analysis, reports, session replay, heatmaps, and revenue reporting. That makes it a measurement tool for product decisions, not a general PO workspace.

## Why It Is Useful For Product Owners
Umami helps a PO move from opinions to evidence. For backlog refinement, it can show which pages, entry points, and user journeys deserve attention. For prioritization, it gives usage, retention, funnel, cohort, and revenue signals that can separate real problems from loud anecdotes.

For discovery, heatmaps and session replay can expose confusing screens or ignored calls to action. For roadmap planning, trend and segment data can support decisions about onboarding, activation, retention, and monetization work. For stakeholder alignment, shared reports can make tradeoffs less political because the conversation starts from observed behavior.

## How I Would Actually Use It
1. Track the activation path for a new feature and review page views, custom events, and funnel completion before calling the launch successful.
2. Use heatmaps on a pricing, onboarding, or dashboard page to see whether users interact with the controls the roadmap assumes are important.
3. Build a retention view for a core workflow so backlog prioritization is tied to repeat usage, not just first-week adoption.
4. Segment traffic by acquisition channel, plan, region, or customer type to avoid optimizing for the wrong user group.
5. Review session replays for failed or abandoned flows before writing acceptance criteria for a UX fix.
6. Share a focused dashboard with stakeholders before roadmap reviews so debates start with behavior data.
7. Use revenue reporting where applicable to connect product changes to monetization impact, especially for pricing or packaging work.

## Limitations / Watch Outs
Umami is still an analytics system, so a PO will need engineering or data help to instrument meaningful events. If the team only installs page tracking, the product insight will be shallow. It also overlaps with tools already covered in this vault, especially PostHog, OpenPanel, Countly, and Metabase, so the reason to choose Umami is simplicity and privacy, not maximum feature breadth.

Session replay and heatmaps can create privacy and governance concerns if the team records sensitive screens. Self-hosting adds operational work, and the latest release includes database migrations, so upgrades should not be treated casually. It is not a requirements tool, roadmap tool, or backlog system.
