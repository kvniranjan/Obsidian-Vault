# kanboard

## Verdict
Kanboard is worth a product owner's time if the need is a simple, self-hosted Kanban system for backlog flow, task ownership, swimlanes, subtasks, comments, and lightweight delivery tracking. It is not a modern product discovery or roadmapping suite, and the maintainers explicitly say it is in maintenance mode. That is a real limitation, but for teams that want a low-friction board without SaaS overhead, it is still practical.

## What It Is
Kanboard is a self-hosted Kanban project management application. It is a software tool, not a template library or reading list. The repo contains the application source, Docker and database setup files, plugins support, CLI entry points, tests, documentation links, release history, and integration surfaces such as webhooks and API procedures.

## Why It Is Useful For Product Owners
For backlog refinement, Kanboard gives a PO a visible queue of tasks, subtasks, comments, tags, categories, and due dates. For prioritization, swimlanes and columns make it easy to separate discovery, ready-for-dev, blocked, in-progress, and shipped work. For stakeholder alignment, the board can become a shared source of truth for status instead of scattered chats and spreadsheets. For delivery coordination, automatic actions, notifications, project analytics, and calendar feeds help expose stuck work and aging backlog items.

It is weaker for discovery, experimentation, and strategy. You will need separate tools for research synthesis, survey analysis, feature flags, metrics, and roadmap storytelling.

## How I Would Actually Use It
1. Create one project board per product area and keep columns brutally simple: `Inbox`, `Needs refinement`, `Ready`, `In progress`, `Blocked`, `Done`.
2. Use swimlanes for initiative-level separation, such as onboarding, retention, reporting, and technical debt.
3. Turn every vague stakeholder request into a task with a short problem statement, expected user impact, acceptance criteria, owner, and due date.
4. Use subtasks for engineering, design, data, legal, or operations dependencies so handoffs are visible.
5. Review project analytics weekly to identify columns where work is aging instead of relying on status theater.
6. Add automatic actions for repetitive hygiene, such as assigning categories, moving overdue tasks, or triggering notifications.
7. Use the API only if the team wants to sync work with another system. Do not start there unless manual board usage is already working.

## Limitations / Watch Outs
- The repo is explicitly in maintenance mode. Expect fixes and regular releases, not major product innovation.
- The UI will not feel like a modern SaaS product management platform.
- Setup is still self-hosted PHP software. A PO can evaluate it, but an admin or engineer should own production deployment.
- It is a delivery coordination tool, not a full product operating system.
- It will not solve discovery, customer feedback intake, experiment tracking, or roadmap prioritization by itself.
- If the team already uses Jira, Linear, Azure DevOps, or GitHub Projects well, Kanboard may add duplicate process instead of clarity.
