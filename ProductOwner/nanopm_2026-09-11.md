# nanopm

## Verdict

nanopm is worth a product owner's time if the team works in a coding-agent or Git-based workflow and wants product decisions to persist as working artifacts. It covers discovery, opportunities, strategy, roadmaps, PRDs, breakdown, feedback, retrospectives, and handoffs instead of stopping at prompt templates. It is not a finished product-management system, so expect setup work, rough edges, and adaptation to your team's tracker and governance.

## What It Is

nanopm is an installable PM skill pack for AI coding agents. It is primarily a collection of `SKILL.md` workflows plus shell tooling, connectors, typed JSONL state, and a Markdown wiki under `.nanopm/`. It is not a backlog UI or a replacement for Linear, GitHub Issues, or Jira. An optional Swift macOS viewer browses the generated artifacts, but the core workflow runs in the agent and terminal.

## Why It Is Useful For Product Owners

- Backlog refinement: `/pm-breakdown` turns a chosen PRD into tasks and can hand them to GitHub, Linear, OpenSpec, gstack, or a human.
- User stories and acceptance criteria: `/pm-prd` produces a structured product spec before implementation and keeps the riskiest assumption visible.
- Discovery: `/pm-discovery`, `/pm-add-feedback`, and `/pm-opportunities` preserve source feedback, cluster themes, and rank user problems instead of jumping straight to features.
- Prioritization: `/pm-strategy`, `/pm-solutions`, and `/pm-roadmap` compare options, name tradeoffs, and connect outcomes to roadmap choices.
- Stakeholder alignment: `/pm-weekly-update`, objectives, strategy, and roadmap artifacts create a durable shared record rather than a one-off chat answer.
- Metrics and experimentation: the workflow asks for measurable outcomes, falsification, and validation tests before a PRD is treated as ready.
- Delivery coordination: connectors can read GitHub, Linear, Productboard, PostHog, Notion, calendar, Slack, and other sources, with a manual fallback when integrations are unavailable.

## How I Would Actually Use It

1. Install the Codex target and create `.nanopm/` in one product repository.
2. Run `/pm-vision-mission`, `/pm-product`, and `/pm-personas` to establish the minimum context the later skills reuse.
3. Feed interview notes, support tickets, and sales objections through `/pm-add-feedback`, then run `/pm-opportunities` to build a ranked problem set with source references.
4. Use `/pm-solutions` on one high-value opportunity to compare engineering, design, and business options before choosing a direction.
5. Run `/pm-roadmap` and `/pm-prd` so each near-term item has an outcome, scope, non-goals, success measure, and falsification condition.
6. Run `/pm-breakdown` to create delivery-sized work and choose the appropriate handoff target instead of copying a PRD into a tracker manually.
7. Use `/pm-standup`, `/pm-retro`, and `/pm-weekly-update` to compare planned outcomes with actual delivery and keep stakeholders current.

## Limitations / Watch Outs

- It is aimed at solo founders, engineers without a PM, and small teams. A mature product organization may find the opinions and ceremony too prescriptive.
- The core interface is an AI coding agent and filesystem. Product owners who need a polished collaborative backlog UI still need Linear, Jira, GitHub, or another system.
- Integrations are tiered, but anything beyond manual mode requires connector configuration, credentials, or an available MCP tool.
- The repository is young and has weak community proof: 48 stars, 2 forks, 33 open issues, no GitHub release object, and no listed topics.
- Version signals are messy. The README and changelog say `0.26.0`, while the newest Git tag exposed by the API is `v0.11.1`.
- The optional macOS viewer is explicitly described as an early throwaway prototype and its run features execute Claude Code, even though the core skill pack supports Codex.
- The installer is a remote shell script. Review it before using it in a controlled environment, and pin a commit or local checkout if reproducibility matters.
