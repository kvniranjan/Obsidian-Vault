# rtmx

## Verdict

RTMX is worth a product owner's time when the team needs requirements to stay connected to implementation and tests. It is a real Go CLI, not a prompt collection: requirements live in a Git-tracked CSV, status is derived from verification, and CI can fail on unhealthy traceability. It is not a backlog replacement, and the setup is too technical for a PO who cannot get engineering buy-in.

## What It Is

RTMX is a command-line requirements traceability tool written in Go. It stores a requirements database in `.rtmx/database.csv`, keeps detailed requirement Markdown files under `.rtmx/requirements`, links requirements to tests, and derives status from test results rather than manual ticket updates. It also includes graph and critical-path analysis, GitHub Actions validation, a JSON-RPC MCP server, and release tooling. It is software plus a repository workflow, not a template-only library or a hosted backlog product.

## Why It Is Useful For Product Owners

- Backlog refinement: turn vague backlog items into uniquely identified requirements with specs, dependencies, priority, and verification links.
- Acceptance criteria: express the expected behavior in requirement files and require tests to prove the requirement is complete.
- Prioritization: use `rtmx next --one` and `rtmx backlog` to surface the highest-priority unblocked work and critical path.
- Stakeholder alignment: show a Git diff for requirement changes and use `rtmx status` to discuss what is complete, partial, blocked, or missing.
- Roadmap planning: group requirements into named phases and inspect phase completion instead of reporting roadmap progress from manually maintained percentages.
- Delivery coordination: run `rtmx health` to find orphaned tests, stale references, circular dependencies, and other traceability failures.
- Agent-assisted delivery: let an AI agent query requirements through the MCP server while keeping the source of truth in the repository.

## How I Would Actually Use It

1. Pilot RTMX on one risky initiative, such as payments or identity, and create one requirement per externally meaningful behavior.
2. Ask engineering to add a stable requirement ID to each acceptance test, then use `rtmx verify` in the team's normal CI pipeline.
3. Use `rtmx backlog` during refinement to identify blocked work and missing dependencies before sprint commitment.
4. Group requirements into roadmap phases and use `rtmx status` for a weekly delivery readout based on verified evidence.
5. Add the reusable [RTMX validation workflow](https://github.com/rtmx-ai/rtmx/blob/main/.github/workflows/rtmx-validate.yml) as a pull-request gate for requirement health and completion.
6. Connect the MCP server to an approved coding agent so it can read the current requirement, implement against it, and verify the result without inventing scope.
7. Use the repository's own [`.rtmx/database.csv`](https://github.com/rtmx-ai/rtmx/blob/main/.rtmx/database.csv) and requirement files as a worked example before designing a local schema.

## Limitations / Watch Outs

- This is not Jira, Linear, or a stakeholder-friendly backlog UI. It will not replace intake, discussion, notifications, or normal product discovery.
- Adoption requires engineers to maintain requirement IDs in tests and accept Git as the operating surface for delivery status.
- The workflow is technical: Go or a prebuilt binary, repository conventions, CI configuration, and test-framework integration are required.
- The repository is young, with 32 stars, 4 forks, and 4 open issues. The release cadence is encouraging, but community proof is still limited.
- The README reports 10 MCP tools while the integration section describes 7 read tools plus 3 mutation tools. That inconsistency is small but worth clarifying before standardizing on the MCP surface.
- RTMX's benchmark evidence is based on five runs per condition and Claude Sonnet 4. Treat the reported completion lift as an early experiment, not general proof that the tool improves delivery.
- The Python CLI is deprecated with an announced end-of-life date of 2026-09-25. New adopters should use the Go binary and verify migration behavior if they inherit an older RTMX setup.
