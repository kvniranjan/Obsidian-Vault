# clarity

## Verdict
Clarity is worth a product owner's time if the product has meaningful web traffic and too many debates are based on opinions. It gives practical behavioral evidence through session replay, heatmaps, and interaction capture, which helps a PO separate real UX friction from loud anecdote. It is not a roadmap or backlog tool, so do not pretend it replaces discovery interviews, analytics instrumentation, or prioritization discipline.

## Why This Repo Was Picked
This repo won because it gives a PO usable evidence for real product questions: where users rage click, abandon flows, misread screens, or fail to complete tasks. ## What It Is
Clarity is an open-source behavioral analytics library. The repository contains the client instrumentation package, decoding logic, visualization code for session replay, a Chromium devtools extension, tests, scripts, and contribution docs. It is the code behind Microsoft's hosted Clarity service, but the repo itself is a developer-facing analytics library rather than a polished PO workspace.

## Why It Is Useful For Product Owners
Clarity helps with discovery by showing what users actually do instead of what stakeholders assume they do. It supports backlog refinement by turning observed friction into sharper bugs, UX improvements, and acceptance criteria. It helps prioritization when a PO can point to repeated behavior patterns, not just isolated support tickets. It also supports stakeholder alignment because session replays and heatmaps are concrete evidence when teams argue about whether a flow is confusing.

## How I Would Actually Use It
1. Review session replays for the top failed funnel each week and convert repeated friction into backlog items with reproduction notes.
2. Use heatmaps before redesigning a page to see which elements users ignore, overuse, or mistake for controls.
3. Pair Clarity evidence with support tickets so a bug report includes both user pain and observed behavior.
4. Watch first-run sessions after a launch and check whether users understand the intended path without extra help text.
5. Create acceptance criteria for UX fixes using observed failure modes, such as rage clicks, dead clicks, form confusion, or repeated backtracking.
6. Bring short replay clips or summarized patterns into stakeholder reviews when prioritization is stuck on opinion.

## Limitations / Watch Outs
Clarity can show what happened, but it does not automatically explain why. Privacy review matters, especially if the product handles sensitive data, even though the README says sensitive content is masked by default and masking options exist. Product owners will still need engineering help for installation, event context, consent rules, and production rollout. The repo is also not the same thing as the hosted dashboard experience, so a nontechnical PO should start with the hosted product or a developer-supported implementation.
