# core

## Verdict

This is worth a product owner's time if the team builds in Git and suffers from vague requirements, undocumented decisions, or specs that drift from implementation. It is not a backlog UI or a plug-and-play product tool, but it gives the PO a usable contract for behavior, roles, acceptance scenarios, decisions, and definition of done. Skip it if the team will not adopt repository-based documentation or run Node and shell checks in CI.

## Why This Repo Was Picked

The repository connects product work to delivery mechanics instead of stopping at templates. Its product-owner guidance defines who the work serves, turns behavior into Given/When/Then scenarios, puts open decisions into records, and keeps a single ordered backlog with a definition of done. The standard also ships checks for structure, drift, facts, and spec-to-code coupling, which makes it more useful for a team trying to improve execution than another prompt collection. It won over the alternatives because it is current, low-dependency, and explicit about the PO's responsibilities while still acknowledging the engineering handoff.

## What It Is

`repository-standards/core` is an agent-first repository standard, not a standalone project-management application. It provides a normative specification, product and development working guidance, decision-record conventions, capability-spec templates, a Markdown-native backlog format, adoption and alignment workflows, and dependency-light scripts that verify repository structure and drift. The PO-facing layer sits beside engineering and agent workflows so the repository becomes the shared source of truth.

## Why It Is Useful For Product Owners

- Backlog refinement: each item names a source, owner role, rationale, and observable definition of done.
- User stories and acceptance criteria: capability specs require job stories plus Given/When/Then scenarios before implementation.
- Discovery: meeting notes and unresolved questions can be routed into ideas, decisions, specs, or backlog work instead of being lost in chat.
- Prioritization: backlog order is based on risk and leverage, with explicit scope counts for adoption work.
- Stakeholder alignment: business decisions use BDRs and product records, while technical decisions use ADRs, giving disagreements a durable home.
- Roadmap planning: the alignment scope block counts specs, decisions, drift, and guards, making a migration plan discussable.
- Delivery coordination: the PO owns behavior and what done means, while developers and agents own buildability and execution.
- Quality control: CI checks can expose stale specs, missing links, and unverified structure before a release review.

## How I Would Actually Use It

1. Start a feature by writing the user role, desired behavior, and value in plain language, then use the clarify gate to remove open questions before planning.
2. Turn a discovery meeting into a short record and classify each output as an idea, decision, capability spec, or backlog intent.
3. Replace vague backlog cards with rows that name the source, owner, risk or leverage, and a testable definition of done.
4. Write Given/When/Then acceptance scenarios before engineering estimates the work, then link the capability to the code area in the same change.
5. Use a BDR for a contestable product choice such as target segment, rollout scope, or data retention, so the team does not relitigate it in chat.
6. Run an assessment-only adoption pass on an existing product repository and use the counted alignment scope to negotiate a first delivery slice.
7. Review the verification output during refinement or release readiness and treat nonzero drift as work, not as a documentation nicety.

## Limitations / Watch Outs

- It is a repository standard, not Jira, Linear, Productboard, or a stakeholder-facing roadmap board.
- Adoption requires Git discipline and a team willing to keep product knowledge beside code.
- The shipped checks require a Node runtime, POSIX shell, and `jq`; teams on incompatible environments must record what they cannot run.
- The standard is living and targets latest, so a team must manage updates rather than pinning a stable product version.
- Only 4 stars and 2 forks provide weak independent adoption evidence; the author's production use is not the same as broad validation.
- The framework can create documentation overhead if the team records every trivial change as a formal spec or decision.
- Mechanical drift checks cannot prove that the product problem is important, the user evidence is sound, or the acceptance criteria reflect reality.
- The backlog is intentionally not a second issue tracker. Teams still need a clear adapter or process for execution state in GitHub Issues, Jira, Linear, or another tracker.
