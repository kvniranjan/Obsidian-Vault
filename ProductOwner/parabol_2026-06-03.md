# parabol

## Verdict
Parabol is genuinely worth a product owner's time if the team needs better sprint planning, estimation, retrospectives, and meeting follow-through. This is not another PM reading list; it is a working collaboration product that turns team conversations into estimates, decisions, tasks, and action items. The downside is clear: self-hosting is not lightweight, so most POs should start with the hosted demo or SaaS path before asking engineering to run it.

## What It Is
Parabol is an open-source collaborative workspace for agile teams. The repository contains the application code for retrospectives, sprint poker, check-ins, async standups, pages, tasks, real-time collaboration, GraphQL API support, and integrations. It is a software product, not a template library, framework document, prompt collection, or curated list.

## Why It Is Useful For Product Owners
For backlog refinement, Parabol can pull issues from Jira, GitHub, GitLab, Linear, and Azure DevOps into sprint poker so sizing happens close to the actual work items. For prioritization and delivery coordination, it records estimates, tasks, discussion outcomes, and follow-up actions instead of letting decisions die in meeting notes. For stakeholder alignment, Pages and meeting summaries can preserve the reasoning behind tradeoffs and sprint commitments. For retrospectives, it gives structure to reflection, grouping, voting, discussion, and action assignment. For team health and delivery risk, async standups and check-ins make blockers visible before they become missed commitments.

## How I Would Actually Use It
1. Run sprint poker from the real backlog and push estimates back to Jira, GitHub, GitLab, Linear, or Azure DevOps.
2. Use retrospectives to identify recurring delivery problems, then convert only the top voted issue into a tracked action item.
3. Run async standups for distributed teams and scan blockers before the daily sync.
4. Keep sprint planning notes in Pages so estimates, decisions, and action items live with the meeting that produced them.
5. Use check-in meetings for cross-functional product syncs where every topic needs an owner or explicit non-decision.
6. Export or share meeting summaries with stakeholders after planning and retros instead of rewriting status updates from scratch.
7. Trial the no-login retro demo before committing engineering time to self-hosting.

## Limitations / Watch Outs
Parabol is useful, but it will not fix weak product discipline. Bad backlog items, vague acceptance criteria, and indecisive stakeholders will still produce bad meetings. Self-hosting has a real burden: Node.js, PostgreSQL, Valkey, Docker-oriented setup, environment configuration, and enough operational ownership to keep a collaboration tool reliable. The license situation needs attention because GitHub shows an unknown license file plus AGPL-3.0 COPYING, and the README describes dual licensing. If the team already runs excellent planning and retros in Jira, Linear, Miro, or FigJam, Parabol may duplicate tools instead of simplifying work.
