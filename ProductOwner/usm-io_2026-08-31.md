# usm.io

## Verdict

This is worth a product owner's time if the team wants a simple, Git-native user story map without adopting another backlog SaaS. It turns JSON, Markdown, and HTML into an interactive map and linked story-card pages, including acceptance criteria and tags. It is not a current, actively maintained product, so treat it as a lightweight workflow pattern or a small internal tool rather than a strategic platform choice.

## What It Is

`usm.io` is a Node.js library, not a hosted backlog application or a template-only repository. It reads a structured `usm.json` plus optional Markdown or HTML card packages, then renders an HTML user story map and linked card websites. The repository includes source code, tests, documentation, an example project, assets, and a changelog.

## Why It Is Useful For Product Owners

- Backlog refinement: represent activities, steps, and stories in a hierarchy that exposes missing slices and oversized work.
- Roadmap planning: group stories into named releases and see the release slices across the whole journey.
- User stories: keep story titles and descriptions in version control beside implementation work.
- Acceptance criteria: store acceptance criteria directly on cards so refinement output is visible in the generated map.
- Stakeholder alignment: publish a static HTML map that gives stakeholders a readable journey and release view.
- Delivery coordination: use tags such as `needs-refinement` or `stakeholder-x` to mark follow-up work and style or filter cards.
- Traceability: review backlog changes through normal pull requests, commits, and repository history.

## How I Would Actually Use It

1. Create an `input/usm.json` with the product journey as activities, steps, and user stories.
2. Add releases such as `MVP`, `beta`, and `later`, then assign each story to a release to expose the first usable slice.
3. Put detailed story notes in `input/cards/<story-id>/index.md`, including context, open questions, and decision links.
4. Add acceptance criteria to every story that is close to delivery, rather than leaving them in a separate ticketing system.
5. Add tags for refinement state, stakeholder ownership, or risk, then use the generated classes for simple visual cues.
6. Run the renderer in CI on every push and publish the generated static site for product, design, and engineering review.
7. Use pull requests to review backlog changes with engineers and stakeholders before a story enters a release slice.

## Limitations / Watch Outs

- The repository has had no push since 2023-07-18 and has 14 open issues, so current Node.js compatibility and maintenance should be verified before adoption.
- The README and package metadata disagree on version signals: the latest GitHub release is `v3.2.1`, while `package.json` reports `2.3.3`.
- It is a renderer, not a full backlog system. It does not provide permissions, workflow automation, notifications, analytics, integrations, or hosted collaboration.
- The JSON plus card-package model requires repository discipline and a build step. Teams that need rapid non-technical editing may reject it.
- The generated map can become difficult to scan if the product journey is too broad or stories are not kept small.
- A PO still needs to define the story map and acceptance criteria. The tool visualizes backlog structure; it does not validate product decisions.
