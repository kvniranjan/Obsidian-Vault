# POSEIDEN

## Verdict
POSEIDEN is worth a product owner's time if the pain is backlog hygiene, not generic roadmapping. It gives a PO a concrete lens over Azure DevOps, GitHub, and GitLab work items, pipelines, and pull requests, then turns drift into flags, reports, and a stakeholder recap. It is early and technical, so do not treat it as a plug-and-play Jira replacement.

## What It Is
POSEIDEN is a backlog hygiene and delivery visibility tool. It polls work trackers and CI systems, normalizes work items, pipelines, and pull requests, evaluates them against configurable rules, and shows the result through a web or desktop UI plus a CLI. It is a working software repo, not a template library or curated list.

The repo includes a multi-crate Rust workspace, a dependency-light HTML and JavaScript frontend, Docker and Helm deployment assets, a Tauri app shell, CLI commands, documentation, and a committed demo tenant bundle. It supports standalone local use with SQLite, portable mode, hosted multi-user mode behind ingress auth, and repointed clients.

## Why It Is Useful For Product Owners
POSEIDEN maps cleanly to backlog refinement because it flags untagged, stale, missing-tag, disallowed-tag, pull-request, and pipeline issues. It helps prioritization and triage by exposing what needs attention before planning meetings. It helps stakeholder alignment through reports and the Recap feature, which turns closed work into a shareable HTML deck skeleton. It helps delivery coordination by connecting work items, PRs, and pipeline health in one view.

The most practical PO value is that it works with tools teams already use instead of asking the PO to move the team into a new tracker. Azure DevOps gets limited write-back for state, tags, and work-item to PR links; GitHub and GitLab are currently read-focused.

## How I Would Actually Use It
1. Import the demo tenant, run `poseiden poll`, and use the seeded backlog to see whether the flags and reports match how your team thinks about hygiene.
2. Define required tags such as `team:*`, `type:*`, `area:*`, and `source:*`, then use `poseiden lint` before refinement to find items that are not ready for planning.
3. Create a team rule set for stale states, for example stories sitting too long in `In Progress`, then review that list before delivery standups.
4. Use the Work Items view to clean tags and state on the worst Azure DevOps items instead of doing a broad, risky tracker cleanup.
5. Use Reports to build a lightweight delivery review around closed items, pipeline success rate, and work by tag.
6. Generate a Recap deck for a monthly stakeholder update, then fill in the missing narrative and screenshots instead of starting from a blank slide.
7. Put `poseiden lint --json` into a CI or scheduled job if the team wants objective backlog hygiene checks without another dashboard ritual.

## Limitations / Watch Outs
This is young software with no star or fork signal at scan time and 10 open issues. Setup is not trivial: local use still assumes comfort with binaries, SQLite state, provider credentials, and config import; hosted use adds Docker, Helm or another container host, ingress auth, and operational ownership. GitHub release objects were not visible through the API even though the changelog documents `0.1.0`, so distribution maturity needs a real install check before team adoption.

It is also deliberately not a full workflow replacement. It reports and cleans backlog hygiene, but it is not a sprint planner, PR reviewer, CI controller, messaging bot, or full board editor. GitHub and GitLab write-back are not the main path today; Azure DevOps has the stronger write-back story.
