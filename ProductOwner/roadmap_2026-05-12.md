# roadmap

## Verdict
This is worth a product owner's time if the team needs a lightweight public roadmap with voting, comments, and GitHub issue handoff. It is not a strategy tool and it will not tell you what to build. It is useful because it turns roadmap visibility and customer requests into an operational workflow instead of another static slide.

## What It Is
Ploi Roadmap is a self-hosted roadmapping application built with Laravel and PHP. The repository contains the application code, install instructions, Docker setup, role model, GitHub integration, SSO configuration, testing instructions, and deployment guidance. It is a software tool, not a template library, prompt collection, or product-management framework.

## Why It Is Useful For Product Owners
- Roadmap planning: publish planned, live, and untriaged items in a format stakeholders can inspect.
- Prioritization: use votes and comments as one input when deciding which requests deserve discovery or delivery effort.
- Discovery: collect feature requests and problem statements from customers instead of relying only on internal opinions.
- Backlog refinement: convert validated roadmap items into GitHub issues when the team is ready to scope work.
- Stakeholder alignment: give sales, support, leadership, and users a shared view of what is planned and what is not.
- Delivery coordination: move items across boards as work progresses and keep feedback attached to the original request.
- Customer communication: close the loop when an item moves to planned, in progress, or live.

## How I Would Actually Use It
1. Create separate projects for major product areas so feedback does not become one giant undifferentiated request pile.
2. Review top-voted items before roadmap planning, then tag each as investigate, reject, already planned, or needs more evidence.
3. Link roadmap items to GitHub issues only after the problem is understood and acceptance criteria are clear.
4. Use comments to ask follow-up questions on vague requests before turning them into backlog work.
5. Give support and customer-facing teams a standard place to submit requests instead of scattering them across Slack.
6. Use the live and planned boards in stakeholder updates so roadmap status is not trapped in a slide deck.
7. Export or summarize highly active items before quarterly planning to separate real demand from one-off noise.

## Limitations / Watch Outs
- This needs engineering or ops help to run properly. A PO should not pretend self-hosting a Laravel app is a casual admin task.
- Voting is signal, not strategy. Loud users can distort priority if you do not segment feedback by customer value, revenue, risk, or product goal.
- The repository is focused on roadmap operations, not product discovery, analytics, experimentation, or requirements quality.
- The changelog file fetched during the scan was empty, so release notes are not a strong way to understand recent changes.
- Public roadmap tools can create expectation debt if the team publishes speculative work and then fails to communicate changes.
- If the company already uses Productboard, Canny, Jira Product Discovery, Aha, or Linear customer requests well, this may be duplicate infrastructure.
