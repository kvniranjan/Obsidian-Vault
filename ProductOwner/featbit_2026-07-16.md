# featbit

## Verdict
FeatBit is worth a product owner's time if the team ships risky features, staged launches, entitlements, or experiments. It is not a standalone PO tool, so do not waste time on it unless engineering will wire the SDKs and events. Once that setup exists, it gives a PO a concrete way to control rollout scope, inspect adoption, and make launch decisions without turning every release change into a deploy request.

## What It Is
FeatBit is an open-source, self-hostable feature flag and experimentation platform. It includes a web portal, backend services, Docker and Kubernetes deployment paths, SDKs, targeting rules, segments, flag insights, audit logs, approval workflows, scheduled flag changes, APIs, SSO, webhooks, and integrations. For a PO, it is best understood as release-control and experiment infrastructure, not as a backlog or roadmap system.

## Why It Is Useful For Product Owners
- Backlog refinement: separate "build the capability" from "release it to users" so stories can include rollout rules and kill-switch expectations.
- Acceptance criteria: define target segments, default behavior, rollout percentage, event checks, and rollback criteria before development starts.
- Prioritization: test a feature with a small cohort before committing to full launch or follow-on backlog work.
- Discovery: expose variants to defined user groups and use experiment results or flag insights as evidence.
- Stakeholder alignment: give support, sales, compliance, and leadership a clear release plan instead of vague "it is deployed" status.
- Roadmap planning: stage risky roadmap items by market, account, plan, geography, or beta cohort.
- Delivery coordination: use audit logs, scheduled changes, approvals, and webhooks to reduce release confusion.

## How I Would Actually Use It
1. Add a "flag plan" section to every risky feature story: flag name, owner, target cohort, default state, rollout schedule, and rollback trigger.
2. Start beta features at 1 percent or with named customer segments, then expand only after support and product metrics look clean.
3. Use targeted experiences to give sales or customer-success accounts controlled early access without branching the product.
4. Run a feature-level A/B test when the debate is measurable, such as onboarding copy, pricing-page flow, or default settings.
5. Review flag insights during launch check-ins and convert the findings into keep, rollback, expand, or iterate decisions.
6. Use approval requests and audit logs for high-risk changes where compliance, support, or leadership needs traceability.
7. Clean up stale flags during backlog grooming so temporary release controls do not become permanent product debt.

## Limitations / Watch Outs
- This needs engineering integration. A PO cannot get value from it by reading the README alone.
- It is open core. GitHub metadata says MIT, but the README says some features have licensing restrictions and require a license key.
- Feature flags can create product debt fast if nobody owns expiry, cleanup, naming, and documentation.
- Experimentation still needs proper event design, sample size judgment, and guardrail metrics. The tool will not fix weak measurement.
- Self-hosting means the team owns uptime, access control, backup, upgrades, and privacy review.
- It is not a replacement for Jira, Linear, Productboard, roadmaps, research notes, or stakeholder decision logs.
