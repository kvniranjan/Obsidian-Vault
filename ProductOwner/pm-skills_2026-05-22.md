# pm-skills

## Verdict
This is genuinely worth a product owner's time if they already use AI tools for product work. It gives reusable, inspectable instructions, templates, workflows, and examples for common PO artifacts instead of forcing you to rewrite prompts every time. The catch is obvious: if your team does not want AI-assisted product writing, this repo becomes shelfware.

It won because it directly supports the work product owners actually produce: PRDs, user stories, acceptance criteria, hypotheses, stakeholder summaries, OKRs, journey maps, prioritization outputs, meeting artifacts, and discovery workflows. The repo is not just a reading list. It contains executable-ish Markdown skill files, templates, examples, slash command mappings, workflow chains, docs, and release notes.

## What It Is
`pm-skills` is a product-management skill library for AI agents. It is mainly a Markdown-based template and workflow repo, not a traditional SaaS app. The repository contains skill instructions, reference templates, worked examples, slash command definitions, workflow chains, setup docs, release notes, and a sample output library.

The practical unit is a skill folder, usually with a `SKILL.md` plus reference material. A PO can use those files inside compatible agent tools, or just read and adapt the templates manually.

## Why It Is Useful For Product Owners
- Backlog refinement: use the user story, acceptance criteria, and PRD skills to convert rough ideas into clearer backlog items.
- Prioritization: use the prioritization framework skill to compare RICE, ICE, MoSCoW, weighted scoring, and Kano instead of pretending one framework fits every decision.
- Discovery: use problem statement, hypothesis, opportunity tree, interview synthesis, survey analysis, and journey map skills to move from opinions to structured evidence.
- Stakeholder alignment: use stakeholder summaries, meeting briefs, recaps, and update artifacts to reduce vague status conversations.
- Roadmap planning: use workflow chains and OKR skills to connect objectives, bets, delivery scope, and learning loops.
- Experimentation: use hypothesis and experiment design artifacts to define what success means before engineering commits time.
- Delivery coordination: use PRDs, acceptance criteria, ADRs, and release-oriented workflows to make handoff to engineering less sloppy.

## How I Would Actually Use It
1. Start with `skills/deliver-prd/` when a feature idea is too vague for engineering and needs scope, success metrics, risks, and non-goals.
2. Use `skills/deliver-user-stories/` after the PRD to turn the concept into INVEST-style user stories with acceptance criteria.
3. Use the prioritization framework skill before roadmap planning meetings so tradeoffs are explicit instead of political.
4. Use meeting agenda, recap, and stakeholder-update skills for recurring stakeholder reviews where decisions keep getting lost.
5. Use journey map and survey analysis skills during discovery to organize qualitative and quantitative signals before writing requirements.
6. Use the workflow chains for feature kickoff or post-launch learning when a single artifact is not enough.
7. Pull examples from `library/skill-output-samples/` to set a quality bar for your own team templates.

## Limitations / Watch Outs
- This repo will not fix weak product judgment. It standardizes artifacts, but the inputs still need real customer evidence and strategic context.
- It is AI-agent oriented. If your workflow is Jira plus Confluence with no AI assistant involved, adoption will be awkward.
- The catalog is growing quickly, which is useful but can create choice overload. Start with one or two skills instead of installing the whole thing and hoping magic happens.
- Some install paths are tool-specific. Claude Code, Cursor, Copilot, Codex, and manual-copy workflows are documented, but your exact environment may still need fiddling.
- The companion MCP server is in maintenance mode, so new users should treat the file/plugin path as the healthier route.
- Templates can create false confidence. A clean PRD that is based on bad assumptions is still a bad PRD.
